# 证据模块：一次分析和一次检查分别证明了什么？

[模块目录](../modules.md) · [两条路线](../learning-routes.md) · [理论入口](../routes/theory.md#evidence) · [实现入口](../routes/implementation.md#evidence)

本模块回答：**怎样把“看到了一个结果”写成有明确前提、范围和依据的结论？** 目标是分清输入约束、分析完成、模型内 outcome、结构验证、具体执行对照和工程检查。

最低准备是 [00 的三种输出](../00-start.md#第三步把输出和手算结果对上)与 [03 的 B/S 区分](../03-cfg.md#2-分清代码块-b-与分析状态-s)。不要求先学完整抽象域；遇到 Top 时先把它理解为这个数值摘要允许任意 word，再在第二单元观察它与完成状态的区别。

前三单元用于阅读任何报告；第四单元适用于准备修改代码或提交 PR 的读者。这里复用现有实验与检查流程，学习目标不是收集更多绿色标记，而是说明每种证据支持哪句话。

## 单元一：同样 Converged，覆盖的是同一组输入吗？

**起点与范围：**做 [06 的调用输入对照](../06-boundaries.md#实验-d同样收敛覆盖的调用输入不同)，只改变未知 calldata 与显式空 calldata。记录两次输入、分支种类和完成状态，暂不研究整个环境参数表。

两份结果都可收敛，但未知长度保留真假分支，空输入只保留 true 分支。先在报告里找到实际环境字段，再写结论：“在这组输入约束、fork 和分析策略下……”；不要把一次空输入分析扩写成任意调用。

理论上，结论的量化范围由输入决定；把范围缩小后得到的结论不能自动扩大。实现上，沿 [`EvmArgs::environment`](../../crates/evm-abstract-cli/src/evm.rs) 到 [`EvmEnvironment`](../../crates/evm-abstract/src/world/environment.rs)，检查省略参数与传入零/空如何形成不同输入。

**停在这里的产物：**一张“两组输入 → 两组分支”的对照表，并能在 JSON 中定位环境。需要解释其他字段时，定点补读[执行与输入模块](execution.md)，无需在本单元枚举全部 CLI 参数。

## 单元二：精度下降、执行失败和未展开区域怎样区分？

**起点与范围：**依次做 [06 的容量实验 A](../06-boundaries.md#实验-a精度下降但分析完成)和[预算实验 B](../06-boundaries.md#实验-b预算用尽传播尚未完成)，再用[实验 C](../06-boundaries.md#实验-c局部交换停下整体传播仍然完成)核对局部事实交换的限制。每次只记录一个变化的配置项。

把三类信息放到三列：值是否变粗、模型内有什么 Return/Revert/Failure、是否还有 frontier。Top 不必导致 Incomplete；Failure outcome 不等于分析器没算完；局部交换达到上限也不等于根工作预算耗尽。

读[诊断、程序失败与分析前沿](../06-boundaries.md#2-诊断程序失败和分析前沿分别看)，在 [`analysis/engine.rs`](../../crates/evm-abstract/src/analysis/engine.rs) 找完成状态与根入口 Failure 的处理，再在 [`analysis/transfer.rs`](../../crates/evm-abstract/src/analysis/transfer.rs) 找具体前沿的产生位置。理论要求是保留未覆盖工作，不能把缺失的结果当成不可达。

**停在这里的产物：**完成 [练习 7](../07-exercises.md#7-分辨值未知和分析没做完)，给每个样例写清状态、退出码和理由。若困惑发生在一条指令内部，转到 [SSA 的前缀单元](ssa.md#单元三mload-只弹出了参数报告该怎样写)，先区分局部进度与整图完成。

## 单元三：结构检查和具体执行样本各能支持什么？

**起点与范围：**读 [06 的三种证据](../06-boundaries.md#3-三种结论需要三种证据)和[测试分类](../06-boundaries.md#6-测试分别核对了什么)。只挑一条已经运行的 SSA 指令或一个跨合约 outcome，不需要阅读全部测试文件。

| 证据 | 本单元核对的问题 | 仍不能据此声称 |
| --- | --- | --- |
| SSA 验证通过 | 定义、使用、前驱与栈形状是否符合该表示的契约？ | 抽象图每条路径都有真实可执行输入 |
| 独立 revm 轨迹被覆盖 | 该具体样本的指令、返回和效果能否对应到抽象结果？ | 所有输入、所有合约都被正确覆盖 |
| Converged | 当前模型和输入下的传播及前沿是否闭合？ | 任意交易有足够 gas，或合约满足任意安全性质 |

实现先在 [`ssa/world/verify.rs`](../../crates/evm-abstract/src/ssa/world/verify.rs) 找一个定义/使用检查，再在 [`cross_concrete.rs`](../../crates/evm-abstract/tests/cross_concrete.rs) 找具体 outcome 的联合覆盖断言：返回数据、storage、余额和日志必须由同一个抽象 outcome 支持，不能从互不相容的路径各取一项。

理论上，有限样本适合找漏覆盖反例，结构不变量适合发现表示错误，它们都需要限定适用范围。选做 [练习 12](../07-exercises.md#12-进阶设计解释一条边为什么存在)时，只设计边的证据说明，不把“图中存在路径”升级为具体执行见证。

**停在这里的产物：**写两句话：一条现有测试确实检查的性质，以及一条即使它通过也不能推出的结论。若需要部分 SSA 的验证范围，定点补读 [SSA 的覆盖单元](ssa.md#单元四块走完了为什么-φ-仍是-partial)。

## 单元四：修改实现后，怎样留下可复核的工程证据？

**起点与范围：**准备交付改动时，按[本地检查的最终提交步骤](../local-ci.md#1-准备最终提交)、[完整门禁](../local-ci.md#2-在本地执行完整门禁)和[记录结果](../local-ci.md#3-核对并记录结果)执行。纯阅读到此只需解释流程，不必为了完成学习额外运行一次构建。

先让一个具体例子说明改动前后的行为；针对受影响的规则选择已有测试或必要的回归；最后在同步 main 的最终干净提交上执行完整门禁。局部测试回答具体回归问题，完整门禁同时检查仓库的测试、格式、文档和打包等要求。

从 [`nix/system.nix`](../../nix/system.nix) 的 checks 汇总追到 [`nix/checks.nix`](../../nix/checks.nix)，理解“跑了哪份检查”；再核对实际命令的完成状态和 Nix 自身退出码。保存 commit SHA、main 基线、命令和结果，才能将证据绑定到别人将审查的代码。

理论上的性质证明与工程门禁仍有不同范围：门禁通过不扩大模型的 gas、输入或跨交易能力。检查后的提交变化会改变证据对象，按[内容变化后的规则](../local-ci.md#4-合并内容变化后重新检查)重新检查。

**停在这里的产物：**一份可让他人定位并复跑的检查记录；若没有修改实现，则给一份已有记录标出被检查提交、执行命令、真实退出码和适用边界即可。

## 怎样判断整个模块已经完成

选一个报告或改动，写出“输入前提 → 观察结果 → 支持证据 → 尚不能推出的结论”。四项都具体到字段、指令、测试断言或提交，而不是只写“已收敛”“测试通过”。

发现问题属于输入范围，回[执行与输入](execution.md)；属于未闭合值流，回 [SSA](ssa.md)；属于快照或复用前提，回[快照与摘要](rpc-summaries.md)。这个模块为其他主题提供验收方法，不要求先按编号读完所有章节。
