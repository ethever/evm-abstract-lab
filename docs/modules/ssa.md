# 值流模块：名字、φ 与部分执行证据

[模块目录](../modules.md) · [两条路线](../learning-routes.md) · [理论入口](../routes/theory.md#ssa) · [实现入口](../routes/implementation.md#ssa)

本模块回答：**看到一个 `%value`，怎样追溯它的来源，并判断这份来源证据是否完整？** 学完后，你应能手画栈中名字的变化，解释普通 φ 的前驱选择，以及部分 SSA 为何保留没有正常结果的指令。

单元一只需会按栈底到栈顶手算 PUSH/ADD，补读 [00 的手算程序](../00-start.md#第二步先手算这个程序)即可。进入单元二的 φ 时，再补 [03 的 B/S 区分](../03-cfg.md#2-分清代码块-b-与分析状态-s)，区分代码位置和分析状态；无需先读完整跨合约或 SMT 章节。

四个单元依次处理名字、完整连接、部分步骤和覆盖判断。命令与完整输出复用第 04 课；每个单元完成自己的记录后，就可以暂停。

## 单元一：两个值定义，为什么能占三个栈槽？

**起点与范围：**从 [04 的 PUSH、DUP、SWAP 实验](../04-ssa.md#1-先分清值名字和栈位置)开始，只读到 φ 章节之前。先在纸上画名字，运行后再对照。

记录三栏：执行位置、栈里的名字、这些名字代表的数值。DUP 复制已有引用；SWAP 换位置。不同 PUSH 即使数值相同，也属于不同定义位置。SSA 的“单赋值”约束静态定义位置，不要求运行时循环只能执行一次。

从理论看，这一步把“值的来源”与“目前在哪个槽位”分开。从实现看，在 [`ssa/build.rs`](../../crates/evm-abstract/src/ssa/build.rs) 找到 DUP/SWAP 分支，检查它们为何复用已有 ID；再看普通结果怎样分配新 ID。

**停在这里的产物：**得到 `[%0, %1, %0]`，并能解释为何标题是 `values=2`。用 [练习 4](../07-exercises.md#4-用名字追踪-dupswap-和-φ)的第一个命令自检，暂不需要解答其中的 diamond。

## 单元二：入口 φ 接收哪个前驱的值？

**起点与范围：**运行 [04 的 diamond](../04-ssa.md#2-分支汇合时怎样给入口值命名)，保留正文的 `--context-depth 0`。随后只补读[循环命名](../04-ssa.md#4-循环为什么不需要无限多个名字)，不用先研究敏感性参数的全部取值。

在同一个 φ 旁分别画两条输入边：从 S1 来接收 `%4`，从 S2 来接收 `%5`。沿每条边各走一次后面的 ADD。再将这张图改成循环：入口给初值，回边给上一轮的结果，静态定义位置保持不变。

理论上，φ 是按前驱选择来源；`abstract {0x1,0x2}` 才是数值摘要。实现上，按 [04 的构建与验证](../04-ssa.md#5-本仓库如何构建和检查-ssa)依次找入口名字分配、块内栈模拟、前驱连接。当前实现给每个入口槽都起名字，所以单输入 φ 也会出现。

**停在这里的产物：**写出 diamond 两条路径分别得到 11、12，说明 φ 为什么不把两个输入相加。能指出 [`ssa/verify.rs`](../../crates/evm-abstract/src/ssa/verify.rs) 对 φ 输入检查的是对应前驱出口，即可结束本单元。

## 单元三：MLOAD 只弹出了参数，报告该怎样写？

**起点与范围：**完整做 [MLOAD 中途停止实验](../04-ssa.md#从块中途停下的实际输出开始)，使用同一份 [`partial-ssa-memory.json`](../../examples/partial-ssa-memory.json)，只改变正文中的 1/32 字节上限。这里不需要真实 RPC，也没有外部调用。

先预测 MLOAD 的结果名字和 ADD 是否出现，再观察输出。上限 1 时，偏移 `%1` 已消费，MLOAD 为 `OperandsConsumed`，留下 `recorded prefix stack: F0: [%0]`；上限 32 时，MLOAD 和 ADD 才分别定义 `%2`、`%3`。两次剩余数值都可为 1，来源却不同。

接着读[指令阶段](../04-ssa.md#一条指令已经走到哪一步)和[效果链](../04-ssa.md#进度和效果链怎样一起读)，按正文加 `--verbose`。`%n` 连接栈值，`!n` 连接粗粒度整机效果，`progress` 说明已走到的阶段；出现新的效果名字不证明 storage 被修改，也不证明指令正常完成。

从 [`transfer.rs`](../../crates/evm-abstract/src/analysis/transfer.rs) 依次找到消费参数、`touch_memory`、提前返回，再到 [`evidence.rs`](../../crates/evm-abstract/src/analysis/machine/evidence.rs) 和 [`ssa/partial/build.rs`](../../crates/evm-abstract/src/ssa/partial/build.rs)核对如何命名这段记录。理论检验是：名字只能对应有证据支持的定义，不能按操作码通常的栈效果补造结果。

**停在这里的产物：**列出两次的已访问 pc、剩余栈、状态和退出码，核对 [练习 13](../07-exercises.md#13-判断部分-ssa-究竟记录到了哪里)的内存表格。能解释 `F0`、栈底 `slot 0` 和 `exit_frames=[[0]]`，就已覆盖这一小步。

## 单元四：块走完了，为什么 φ 仍是 partial？

**起点与范围：**运行 [04 的单输入 partial φ 示例](../04-ssa.md#部分-φ-的输入覆盖哪些边)，再读[状态证据](../04-ssa.md#每个状态的证据是否仍适用)和 [JSON 编号连接](../04-ssa.md#保存-json-并连接状态编号)。只需理解调用结果沿继续边交给 caller，帧与回滚的更多细节可留给[调用模块](calls-state.md)。

追踪 `T0: %14 → %11`，再找到 `ADD %12 %11`。T0 是已支持的失败继续转移；S1 可以执行到 STOP，同时 S0 的未知目标仍留下前沿。T 使用原生机器边编号，不能换成局部投影的 S 编号。

将三项判断写在不同栏：`Current` 是否对应当前入口；当前块记录到了哪一步；整张图的入边覆盖是否闭合。当前构建器对 Incomplete 图统一设 `incoming_complete=false`，不是已经证明每个节点都缺一条边。`open_incoming=[]` 只排除了已记录但尚不能接入的那类入边。

实现核对到 [`ssa/partial/verify.rs`](../../crates/evm-abstract/src/ssa/partial/verify.rs) 即止：它检查已支持的前缀、转移与保留前沿；本仓库完整 SSA 的覆盖与支配检查另有完成图前提。理论上的来源连通，不能代替真实路径可执行性证明。

**停在这里的产物：**完成练习 13 的 φ 问题，并能解释一个 Stale 状态为什么不能拿旧出口为新入口作证。暂不需要实现 φ 消除；[练习 10](../07-exercises.md#10-进阶设计消除多余-φ)是后续设计题。

## 怎样判断整个模块已经完成

拿一条 SSA 指令，指出其操作数定义；拿一个 φ，指出其前驱或 T 输入；拿一份部分报告，指出已观察阶段和未闭合覆盖。三项都要能在输出和源码中对应，不能只复述“SSA 给值起名字”。
