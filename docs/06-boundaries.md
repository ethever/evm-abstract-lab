# 06：知道结果能证明什么

本课目标：区分模型内收敛、精度下降、资源未完成和具体证据，理解以后如何用链上信息改进分析。

## 三句话分别在说不同事实

“工作表收敛”说明已经算完本抽象模型内的传播闭包。“图覆盖某条 revm 轨迹”说明那个具体样本没有被遗漏。“合约不会出现某种行为”则需要针对实际 EVM 状态空间、假设和目标性质的证明。

本仓库提供前两类可检查证据，没有声称第三类。这不是形式验证系统或完整漏洞扫描器。

## 本模型如何看待 EVM 的各部分

| 部分 | 当前模型 | 影响 |
| --- | --- | --- |
| 输入 | 单合约的 legacy runtime bytecode，默认 Osaka，可选 Cancun/Prague，入口 pc=0、空栈 | 不自动提取 creation bytecode，不解码 EOF；EIP-7702 委托标记需提供实际执行代码 |
| 栈 | 高度 ≤1024、有限常量集合或 Top；DUP/SWAP 保留身份 | 集合容量、逐槽独立性影响精度 |
| 纯运算 | 支持 0x01..0x0b 与 0x10..0x1d；Osaka 额外启用 0x1e CLZ，遵循 U256/补码规则 | 未知参数保守返回 Top、布尔集合或域容量容许的 CLZ 结果集合 |
| PC / CODESIZE | 精确常量 | 用来计算目标的表达式可以更精确 |
| calldata/环境/余额 | 读取结果保守抽象，通常为 Top | 不假设某次交易参数或固定 sender |
| 内存 / storage / transient storage | 保留 opcode 与 stack I/O；读取为 Top | MSTORE→MLOAD、SSTORE→SLOAD 的精度尚未保留 |
| hash | KECCAK256 输出为 Top | 没有把未知内存 hash 当作固定常量 |
| CALL / CREATE | 保留参数和结果；不展开外部 bytecode，结果保守抽象 | CFG 只属于当前合约，不覆盖外部合约内部指令 |
| gas / static 模式 / returndata 边界 | 过近似正常继续；忽略这些条件造成的额外故障 | 图可能包含因 out-of-gas 等而不可执行的路径 |
| JUMP/JUMPI | 有限目标逐一验证；Top 覆盖所有真正 JUMPDEST | 未知目标可能产生大量伪边 |
| 停止与可识别异常 | 停止传播并保留访问指令/诊断 | 图的边仅表示正常块间转移，没有异常 sink 节点 |
| 资源预算 | 显式 Incomplete + frontier | 不能用未覆盖区域推断不存在行为；拒绝 SSA |

忽略某些故障条件时选择让程序“可能正常继续”，是为了避免把正常执行路径删掉。分析图可能更大，不能理解为每条路径都能成功执行。

`OpaqueResult` 是“语义被摘要”的提示；`UnknownJump` 是跳转目标精度不足；`InvalidJump`/`StackUnderflow`/`StackOverflow`/`InvalidOpcode` 是模型内的异常路径。它们和预算前沿不同，所以可能与 `Converged` 同时出现。

## 理论上的保守性和工程证据

抽象 transfer 的目标是：具体执行结果始终包含在抽象结果代表的集合中。若输入从精确值放宽到 Top，就不能通过猜测删除真实目标。逐槽 join、Top 跳转展开和有界历史的合并都遵循这个设计。

实现仍可能有 bug，因此需要不同层面的证据：

- 域的随机性质测试核对 join 的交换、结合、幂等与覆盖。
- 字节边界、PUSH 补零、JUMPI 零条件、栈故障等回归检查语义细节。
- SSA 验证器检查唯一赋值、普通 use 的支配和 φ 边参数；反例测试确认它拒绝损坏的 IR。
- revm 分别使用 Cancun/Prague/Osaka 配置具体执行原有六个例子，并用 Osaka 执行 CLZ 跳转例子；实际块入口、边与出栈都被包含，SSA 操作数、φ 边输入和出栈名字对应的具体值逐条核对。纯运算用边界值与随机 256 bit 样本对照；CLZ 另核对零和全部 256 个单置位值。
- CLI 测试核对真实输入/JSON/退出码；Nix 打包后二进制另做例子与 DOT 渲染检查。

有限测试可以发现错误，不能证明覆盖全部合约、全部 calldata 或全部 256 bit 参数。请保留这个证据范围。

## 加入链上状态能提高精度吗

可以，但必须让假设可见。例如在某个固定 block hash 的快照中，已知 storage slot 0 的初始值是一个跳转地址，SLOAD 的 Top 可以收窄到那个值，从而减少 CFG 边。

问题随后变成：快照属于哪个链和区块？进入分析前 slot 0 是否已经被修改？SSTORE 是否可能写到与它相同的符号地址？外部调用或 delegatecall 是否改变了状态？不同交易与重入怎样传递状态？

```text
固定快照 + 明确入口假设
        ↓
初始抽象 storage
        ↓
SSTORE 的强/弱更新、可能别名、外部副作用
        ↓
之后的 SLOAD 摘要
```

只把每次 SLOAD 都替换成“节点此刻读到的值”，会忽略程序中的写入，可能删掉真实路径。未来实现应把固定快照、更新规则和假设写入结果指纹；未知别名时保守扩大，而不是继续沿用旧常量。

本仓库现在不访问节点。链上状态是之后可加入的显式事实源，不是已经存在的功能。

## 下一阶段的合理研究顺序

先提高可观察性和正确性，再增加域的复杂度：trivial-φ 消除与 def-use 查询；内存常量传播；storage 快照及强/弱更新；内部函数恢复与真正调用上下文；带约束的分支假设；更复杂的域与 widening/narrowing；最后再讨论符号执行混合或漏洞性质。

每加入一项，都给出“哪个旧例子变精确了”“哪些新假设引入了”“是否仍覆盖具体轨迹”的证据。不要靠结果更短来判断分析更正确。
